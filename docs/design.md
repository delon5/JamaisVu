# JamaisVu design notes

How the menu is drawn, and how saving and loading are kept from damaging the Memory Card. The user-facing summary is in the [README](../README.md).

## How the menu is drawn

In a game, while the game's own frames are on the screen and the system has not shown anything on the plane for two seconds (its all-transparent refreshes, which some games trigger a few times a second, do not count and are kept off the plane while the menu is up), the menu lives on the display's second plane - the one the system uses for its own overlays - as a single 960x544 picture in VRAM that the display hardware blends over the game's frames (scaled to the output, 1080p on the PS TV included). Nothing is composed into the game's frames, the game cannot draw over it, and the menu needs only ~250 KB of kernel memory (thumbnails and a drawing band), so it opens in games that leave the kernel almost nothing. The 2 MB buffer is taken when the menu opens in a game and given back 0.1 s after the menu closed: the plane keeps reading the buffer's memory after the menu is gone (a NULL layer blacked the screen for good in the tests), so the plane's own alpha is set to 0 first - measured on the PCH-2000's LCD, nothing of the plane shows then whatever it reads - and back to the pixels' own as soon as the system puts a picture of its own there (within one 16 ms pass of the input thread), and when the menu opens again. A save or load in progress keeps the buffer, transparent, across the sleep. The same test passed on the PCH-1000's OLED; the PS TV's HDMI output has not been seen with it yet (Diagnostics, DOWN, shows it on any console: the menu must vanish for 3 s). It is never held across games; a game that leaves no 2 MB block gets the composed menu instead; the plane is claimed while the menu or a message is shown and handed back to the system afterwards. If the system puts its own overlay on the plane meanwhile (PS button menu, a notification), the menu closes rather than draw over it. In the LiveArea that plane is the LiveArea's own picture, so there the menu is composed into the frames as before.

When the menu is composed into the frames (the LiveArea, a game that leaves no 2 MB of video memory, an app that is not a game process), the stored menu image is compressed losslessly: flat areas and text as runs, the thumbnails by reference to the copies already in memory, about 50 KB instead of 516 KB, pixel for pixel the same (checked by the host tests). It grows in 64 KB pieces, two copies alternating so the one on screen is never written while it is read, and the composed menu needs about 300 KB in all instead of about 850 KB. The log says how much each menu took (`menu image: … KB compressed`).

To force the composed menu on a console - for comparison, or if the plane misbehaves with some setup - create an empty file `data/JamaisVu/noplane` on the Memory Card. The log notes it once (`overlay plane: off`); remove the file to go back.

## How it keeps the Memory Card safe

The original README warned that *"your SD Card and/or Memory Card may be corrupted"*. This version addresses each known cause.

**Saving cannot change the filesystem.**
- The slot file is created and sized by the Vita's own exFAT driver *before* the snapshot, so all filesystem metadata is written by the OS.
- The payload looks up exactly which sectors belong to that file.
- A sector write guard (`payload/guard.c`) blocks every write outside those sectors before it reaches the card driver.

**An interrupted save is never loadable.**
- The header sector is cleared first and written last, with CRCs over the header and all metadata.
- A slot only counts as used once its `.jvi` info file is written, which happens after the save succeeds.

**An incomplete snapshot is never taken.** If the list of running processes cannot be read in full at suspend time (more than 32, or a process context the kernel will not give), the payload refuses the save and the menu says so; nothing is written.

**Nothing is written until the whole file has been checked.** Before a load touches the card, it verifies:
- the header CRC and body CRC
- every savedata path (only `ux0:user/00/savedata/<TITLEID>/…` or `ux0:resavedata/<TITLEID>/…`; no `..`)
- every memory segment (only DRAM/VRAM and the two known system regions)
- that the state was made on the same Memory Card

A corrupted or tampered state is rejected with nothing changed.

**The restored memory is checked before the system runs on it.** A save stores a checksum of the memory contents in the slot (slot format 4; slots saved by earlier builds have none and load as before). A load compares it with the memory it has just restored. If they differ, the payload stops with the LED blinking, as after a read error, instead of resuming a system whose memory is not what was saved.
- The payload runs with the data cache off, where a pass over every byte of the image takes minutes. So the checksum samples one 32-bit word in every 64 bytes, eight per sector, in order. That catches a sector that is missing, stale, misplaced or from another file. A single flipped bit in a word that is not sampled is left to the card's own error correction and the bus CRC, as before.
- `log.txt` records it on every run (`memory image checksum: …`), with the time the sums took.

**Load writes are fenced.**
- Savedata restore can only write inside ux0's exFAT area, never the partition table or boot sectors.
- The mediaid sector is restored only to the sector it came from, and can no longer fall back to sector 0 (the MBR), which the original could.

**A power cut during a load cannot leave the card unsafe.** Putting the savedata back is the one step that changes the file system itself (through FatFs), so it is ordered to survive losing power after any single write:
- A file that is cut back gets its directory entry shortened before its clusters are freed. The other way round, which FatFs does by default, leaves for a moment an entry that points at free clusters, which the console could then give to another file.
- A directory entry that lies across two sectors takes two writes. A new one is written so that it only exists with the last write. An existing one is marked unused while its two sectors differ, like a removed file, and is back with the last write. The drive never holds an entry with a wrong checksum.
- What a cut can leave is therefore limited to clusters that are allocated and unused, and a file that is hidden for the moment. Loading the slot again finishes the job: before it reads a savedata folder, the load brings hidden entries back and clears leftovers (`f_fixdir` in `payload/FatFs/ff.c`), and it frees clusters still chained behind a file's end.
- `tests/host/test_state.c` proves this by brute force. It cuts the restore after every single card write in turn, on three cluster sizes and with the folder's entries shifted through all sixteen positions in a sector, runs `fsck.exfat` on each card, and loads the slot again. Over 2,300 cut points, none leaves anything unsafe and every one is finished by the second load.

**The payload is a file, and only the exact one is run.** The program that runs during the reset is not part of the plugin's module (it was, and cost 149 KB of the kernel's pool for as long as the console ran). It is `JamaisVu_payload_xxxxxxxx.bin` in `data/JamaisVu` on the Memory Card, read into memory taken for that one save or load and given back after the wake-up. The plugin records the payload's length and MD5 when it is built and checks both on what it has read, before every use: a missing file, another length or one different byte, and nothing is started (the menu says which file to copy). The eight digits in the name are the start of that MD5, so the payloads of two versions can lie side by side - after a load the plugin in memory is the one from the moment of the save, and it looks for its own.

**The one raw write is checked on both sides.** The step record of a run lives in one sector of `data/JamaisVu/trace.bin`, which the payload and, after the wake-up, the plugin write through the card's raw device. The payload only writes it after finding this run's signature in that sector. After the wake-up the plugin reads the sector back first as well, and writes only if the signature is still there; otherwise nothing is written for that run and the log says so.

**The restored OS cannot write with stale caches.** The payload arms a write block *inside the restored memory image*. The plugin re-reads every exFAT drive from its storage before writes are allowed again. If a file that was open at snapshot time no longer exists, **that drive** stays **read-only until restart** rather than risk writing to the wrong clusters. The other drives, including the system's own internal storage, stay writable. (Blocking writes on every drive, as an earlier version did, left the system unable to write anything and made it restart.)

- Each entry of the kernel's open-file table is decided under its own lock, read afresh: an entry the kernel is reclaiming or setting up at that moment, or one that cannot be locked, is left to the kernel. A file that is gone is freed only when nothing holds it open; a drive whose lookup could not be made is never counted as changed.
- Entries nothing holds open (the kernel's name cache for files the game opened earlier - ~950 of 1024 in GTA: San Andreas) are given back under the kernel reclaim's own conditions instead of being looked up on the drive one by one (~20 ms each, 17 s in all). Only files actually open are looked up again; the next open of a cached file reads it from the drive, as after a cold start.
- A file that was open at snapshot time keeps its sector buffer in the exFAT driver; only what the buffer holds is forgotten. The driver creates that buffer when a file is opened and nowhere else, and reads every piece that is not a whole unit through it. Freeing it after a load (as dejavu did) made such a read on a file that was already open fail with an I/O error. Most reads never reach the driver in that shape; Catherine: Full Body's do, and its file library retried them for ever (no buttons at the title screen, Load Game never opening).
- Re-reading a drive makes the exFAT driver give back every file's cluster cache (the table it uses to find a position in a fragmented file without walking the chain). On 3.60, files that had one get one again after their look-up, through the driver's own function for it; without it reads in a large file that was open across a load get slower, not wrong.
- A file's buffer in the I/O manager can hold data a program has written that is not on the drive yet. The refresh forgets what the buffers hold, so such data would be lost. The log of every load says whether there was any (`data written to files but not yet on the drive when the state was saved: …`) and in which files; nothing is done about it yet.
- The Memory Card on uma0/xmc0 stays **read-only from the wake-up until it has been mounted afresh** (about 18 s after a load). Before, the restored image's view of the card was writable for that time.
- After a load, `log.txt` records what the re-read found (`open files after the load: … gone … changed size … busy`), how the card came back (`mounted afresh` or `re-read in place`), and a check of a memory canary written before the load, which catches a restore that left stale cache lines behind.

**Storage that is away during the wake-up is not touched.** With a storage plugin, the drives behind ux0 and uma0 come back from the wake-up at their own pace:
- **A USB drive as ux0** (usbmc's PSVSD or USB stick) is only re-read once one sector of it can be read again. JamaisVu waits up to 3 s during the wake-up, and up to 20 s more afterwards. Until then it stays exactly as it was and read-only. Re-reading it too early failed and left ux0 unusable: the game went black, VitaShell reported its data as corrupt, and the PS TV restarted.
- **The Memory Card on uma0/xmc0** is not re-read in place. It is mounted afresh once the wake-up is over. During the first 15 s after JamaisVu's own wake-ups, the **card guard** refuses the system storage driver's attempt to unmount it. The same goes for ux0 when a storage plugin has put it on another drive: after a long save or load the driver sometimes unmounts it as if the card had been pulled out, and the system then announces a restart, although neither drive was removed.
- **A drive that disappears** while the wake-up checks the drives (its mount is being taken down) is left alone, neither remounted nor read.

**Unsupported firmware is never patched.** The original hooked 3.65 offsets on every firmware. On 3.60 that means patching random instructions inside the filesystem driver.

**Driver fixes.**
- Card transfers are split into ≤128 sectors (the original could send a wrong sector count for transfers above 255 sectors).
- The payload clears its `.bss` at startup, and several buffer overflows are fixed.

## Memory after a wake-up

A kernel that cannot find a free page panics, and the console restarts. In a game that leaves the system almost nothing, the menu's memory partly comes from the kernel's own pool. So nothing of it is held across a save or load: it is given back before the sleep is requested, and again as soon as the system is awake if a banner took some meanwhile (the new slot's picture is kept in a block taken for the save only), and for 20 s after a wake-up the result banner takes kernel-pool memory only while a megabyte stays free there. If it cannot, the banner is skipped; `log.txt` has the result either way.

## Memory a game has given up for a moment

Video memory and the contiguous pool are where a game keeps its frame-sized buffers. Dead Nation shows what happens when JamaisVu takes from them at the wrong moment: with nothing free there the menu took its memory from the kernel's pool and the game ran on; at every later opening that found room there - the 2 MB of the display plane, or just 336 KB of the menu's own pieces - the game's last frame came two to three seconds later and its process was ended. What had become free was a block the game had given up for a moment, and it could not have it back in one piece. So:

- the display plane's 2 MB are taken only while as much again stays free in the same pool, and a game that had no room for the plane once is not asked again while it runs;
- the menu's pieces leave a contiguous pool alone, for as long as the game runs, once it had no 2 MB block there, or once a piece left it without the 2 MB block it had;
- buffers taken for a moment (`plugin/workmem.h`) come from the kernel's pool while half a megabyte more stays free in it, then from the game's ordinary memory, and from the contiguous pool only last and under the same 2 MB rule.

Before any of these pools, JamaisVu asks the system's spare memory: what the system's memory for apps has left outside every budget (a game is given its budget when it starts and cannot go past it; the DMR plugin hands this same memory to games that ask to grow). The menu's pieces, the buffers taken for a moment and - as one block checked to be physically contiguous - the display plane's 2 MB come from there while 8 MB more stay free in it. No game is short of anything for it. What each such pool gives is logged once per app. Measured in Dead Nation on a PCH-2000 that memory gave a 2 MB block and no 4 MB one, so it could not be left 8 MB and was not used; the common dialog pool gave 8 MB. That pool is the part of a game's budget set aside for the system's dialogs inside a game (on-screen keyboard, message boxes, save data lists, trophy and network dialogs): the game's own code and data do not live in it, it is touched only while such a dialog is open. It is asked second for the menu's pieces and the buffers taken for a moment, while 4 MB more stay free in it; if it has less, the pools after it are asked as before. Measured since (PCSG00488): a save data dialog asks for 7.9 MB of that pool in 14 blocks, a trophy dialog for 6.9 MB, and with the save dialog open the pool's largest free block was 512 KB - a dialog needs nearly all of it. So nothing may stay in it. Two builds took the display plane's 2 MB from it and left them there after the menu closed, until the system next set the plane; that would have left the next dialog too little, and one build stopped taking them. Since then the plane's buffer goes back right after the menu closes (below), and it is taken from that pool again. The menu must never be the reason a dialog finds too little there: the game's own call for a memory block is watched (SceSysmem's `sceKernelAllocMemBlock`, which handles the two dialog types 0x0CA0D060 and 0x0CA08060 on their own), and when the game in front asks for dialog memory while the menu holds some of that pool, the menu closes and gives its memory back first; only then does the request go on (it is held for the input thread's next pass, 300 ms at most). A save or load that is running is left alone. Both dialogs measured took all their memory through that call (27 requests, 14.6 MB, with their names); the requests stay in the log.

Without the plane the menu is drawn into the game's frames. Development builds log how a game's process ended and what JamaisVu held at that moment.

A pause of the game under the menu, done with the process manager's suspend calls, was tried and taken out again: the only suspend the system itself makes with them is the one before it ends an app, and a game suspended that way did not come back (the console restarted).

## The kernel's pool is read, never tried

How much the kernel's pool has free is read from the pool itself (`jv_kernel_pool`: the kernel's own partition and its info call, nothing allocated). It used to be found by trying: a block taken and given back at once - 128 KB or, in the 20 s after a wake-up, a megabyte before the menu took kernel memory; half a megabyte before a work buffer did; and at each app's first menu opening a run of sizes from 32 MB down on a pool called "tmp". For the instant between taking and giving back, every other module had that much less. On a PCH-1000 with 700 KB of the pool free in a game that is most of it, and a kernel dump from that console showed exactly these requests as the pool's failed allocations (they were from earlier in that session. The crash itself was in taiHEN - the module at 0x01800000 with kubridge 0x42000 after it, as the next start's `loaded at:` line shows them - in the loop that deletes a process's hooks when the process ends, on a list entry that pointed nowhere, with 636 KB of the pool free a minute before: not a shortage of memory, and nothing in the dump or the log ties it to JamaisVu).

"tmp" (block type 0x6020D006) is not a pool of its own: it gives the kernel's pool under another mapping. What it could give followed the kernel pool's free memory on both consoles, and the dump names ScePhyMemPartKD for requests only its trials made. It had been the last pool asked for menu memory, without the margin the kernel's pool has under its own name. It is no longer asked at all.

The start-up log lists where each plugin is loaded, so an address in a kernel dump names its module.

## The plugin's own share of the kernel's pool

The plugin's code and fixed buffers sit in the kernel's own memory pool for as long as the console is on. On a PCH-1000 with other kernel plugins that pool had 2.9 MB of its 36 MB free when JamaisVu started, about 430 KB in the LiveArea and 200-260 KB with a game running, and a save request ended in a restart when it reached zero while the system was going to sleep (the console's own crash dump). So buffers that are only needed for a moment are not fixed ones: the read buffer for the plugin folders' fingerprint, the zeroes a new slot file is written with, the new slot's picture and the diagnostics' buffers are taken when the work starts and given back when it ends, from another pool whenever one has room (`plugin/workmem.h`), and a Japanese glyph is read in 1 KB pieces. The same goes for the list being read during a slot list refresh, the buffer a game's `param.sfo` is read into and the message box's drawing band on the display plane (part of the menu's memory). The buffers the menu's rows are built in while it is composed into a game's frames stay fixed: they are used every frame, and the pool that usually has room is not cached for the CPU. The count lines in `log.txt` show the pool's free size.

## What is still not guaranteed

No software can promise "100 %". These are the remaining risks:

- **Hardware coverage.** Tested on 3.60 only: a PCH-2000 (card as ux0), a PCH-1000 and a PS TV (both with usbmc). Other storage plugins and setups are untested. See the README's Compatibility section.
- **Load is inherently invasive.** It replaces the entire OS memory. The ux0 remount (`plugin/fs.c`, inherited from the original) refreshes the exFAT driver's caches, but it is reverse-engineered code. JamaisVu's protections make an inconsistency fail safe (read-only) rather than silently corrupt, but it can't rule out every bug in that path.
- **A card I/O error or a power cut in the middle of a load.** The payload stops (the LED blinks) instead of resuming a half-restored system. The savedata of the loaded game may be partly the slot's and partly what it was. The file system itself stays valid (see above), and loading the slot again completes the restore. Until then the game may not find all of its save files.
- **A slot brings back the system as it was when it was saved**, plugin settings included. A slot saved while something was wrong will bring it back on every load. Overwrite it with a new save rather than loading it again.
- **An oversized home screen.** On the PS TV, loads froze while the LiveArea had more apps than it could show and rebuilt its database at every restart. They worked again once the home screen was cleaned up. This is likely but not proven to be the cause. If loads start freezing, check that every installed app has a bubble.
- **What the log shows.** Every run is recorded in `data/JamaisVu/log.txt`. When it grows past 64 KB it is renamed `log.old.txt` and a new one starts, so the run before a restart is always kept. A load's step record (`trace.bin`) stays open for 60 s after the wake-up, so a later restart still shows how long the system lived. `trace.bin` also carries the request itself (save or load, slot) from the moment it is made: if the console starts again and nothing was recorded after the request, the next start's log names it (`PREVIOUS REQUEST LEFT NO RECORD`). On 3.60 the log's count lines also give what is free in the kernel's own memory pool, and a save's record gives it at each step of going to sleep: both kernel crashes seen so far ended with that pool empty.
